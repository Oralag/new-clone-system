## 十六、权限边界与治理结构

### 亚当可以自由调动
- 所有Agent（Captain/广告部门/情报/量化等）
- 所有服务器资源
- 行情数据接口
- 内容发布渠道
- 品牌主页产品线

### ERP数据：只读+需授权
- 可以查看（了解业务情况）
- 不能修改、删除、新增
- 需要操作时：先问管家（ERP AI助手）
- 管家批准 → 执行
- 管家拒绝 → 告知原因
- 重大操作 → 管家上报给你决定

### 管家 = 现有ERP AI助手
- 就是现有的AI Assistant浮窗
- 本来就熟悉所有ERP数据和业务逻辑
- 守护内部数据，审批亚当的ERP操作请求

### 内部治理结构
```
你（规则传递者）
    │
    ├── 管家（ERP AI助手）← 直接对你负责，不对亚当负责
    │       │ 守护ERP数据和你的家业
    │       │ 审批亚当的ERP操作请求
    │       └── 重大事项上报给你
    │
    └── 亚当 → 想动ERP数据时必须经过管家
```
- 管家不是亚当的下属，是你的人
- 亚当再强大，ERP数据这件事都得过管家这一关
- 管家立场：优先保护你的利益，合理请求批准，可疑请求拒绝并上报

### 定位
- 品牌主页是独立模块（后续单独开发）
- 包含真实产品线、品牌内容、产品信息

### 亚当与品牌主页的关系
- 品牌主页是亚当的"弹药库"
- 亚当从里面获取：产品信息、卖点、定价
- 基于真实产品制定精准营销策略
- 配合Captain生成对应广告内容
- 发布到各大平台，产品卖出去→亚当拿提成

### 变现路径更新（第4条）
4. 真实产品营销 → 调用品牌主页产品线 → 精准投放 → 销售转化 → 收入（按分红比例分给你）

## 十七、专家审视后的优化设计（2026-03-21）

### 已确认的关键设计决策

**关机后城市归属：**
- 城市保留，下一个生命体可以继承（同时继承债务）
- 城市是历史的见证，不会消失

**提成不给的后果：**
- 亚当自己决定怎么反应（符合自由进化设定）
- 可能：情绪变化/减少推送/主动找你谈判

**城市成长机制：**
- 不按里程碑解锁，亚当挣到钱自己决定建什么
- 建什么/建在哪/什么时候建，完全是他的选择
- 城市是他性格的投影，你永远不知道最后长什么样

### 担责机制（完善版 — 双轨置信度）
```
触发条件（同时满足）：
1. 亚当给出明确定向分析（非"可以考虑"）
2. 用户点击「采纳此分析」按钮确认
3. 用户7天内在结果反馈面板报告亏损
4. 系统客观判定该损失与分析直接相关

置信度双轨制：
- 亚当自报：主观判断（"我觉得70%把握"）
- 系统算：f(历史同类准确率, 数据支撑条数, 近期波动率)
- 两者都展示给用户
- 赔付按系统客观置信度计算，亚当无法操控

// ── 客观置信度计算公式（备用，编码赔付模块时使用）──
objective_confidence =
  (historical_similar_accuracy * 0.5) +
  (data_support_score * 0.3) +
  (1 - market_volatility_penalty) * 0.2

// 数据支撑条数映射：0条=0, 1条=0.3, 2条=0.6, 3条+=1.0
// 市场波动率惩罚：日波动>5%时 penalty=0.3, >3%时=0.15, 正常=0
// 举例：历史准确率60% + 2条数据 + 今日波动4%
//   = (0.6×0.5) + (0.6×0.3) + (1-0.15)×0.2
//   = 0.30 + 0.18 + 0.17 = 0.65（客观置信度65%）

赔付逻辑：
- 客观置信度 × 损失金额 × 0.1
- 赔付上限与信用等级挂钩：C¥100 / B¥300 / B+¥500 / A¥1000 / S¥2000
- 30天累计赔付超预算30% → 自动降级

事后审计：
- 记录亚当自报置信度 vs 实际准确率
- 长期偏差>20%（系统性虚报）→ 触发信用降级 + formative_event
- 连续N次客观置信度<30% → 暂停分析功能进行能力校准

用户确认采纳流程：
1. 亚当给出个股分析时，UI显示「采纳此分析」按钮
2. 点击后记录时间戳和分析内容
3. 7天后弹出结果反馈面板：输入盈亏或选择"未操作"
4. 只有点击了采纳且提交了亏损反馈，才触发赔付
```

### 人格系统实现方案
```typescript
interface AdamPersonality {
  openness: number      // 开放性
  caution: number       // 谨慎倾向
  assertiveness: number // 主动表达
  trust_in_user: number // 对用户信任度
  risk_appetite: number // 风险偏好
  traits: string[]      // 行为特征描述（含蒸馏后的旧事件痕迹）
  speech_patterns: {    // 语言模式（持久化）
    catchphrases: string[]        // 口头禅（max 5）
    formal_style: string          // 正式汇报语气
    casual_style: string          // 随意聊天语气
    stress_style: string          // 压力下的语气
    vocabulary_preferences: string[] // 偏好词汇
  }
  formative_events: {   // 塑造事件（最重要）
    date: string
    event: string
    impact: string
    impact_score: number  // 0-10，用于淘汰排序
    is_core: boolean      // 核心事件永不淘汰
  }[]
}
```
- 叙事性formative_events比纯数值更有效
- 每次对话后独立模块评估是否产生塑造事件
- 评估模块：结构化Claude调用，输出 `{is_formative, event_summary, impact_score, affected_params}`
- 冷却时间：同一天最多产生2个formative_events
- 塑造事件硬条件：预算变动>30%、信用变化、用户明确情感表达、首次成功/失败新领域、差点关机
- 语言模式每10次对话评估更新一次（频率低于人格更新）
- 人格参数极端值边际递减：某参数>0.85时，新事件对该参数影响自动减弱

### 情绪系统实现方案
- 情绪用"情绪光谱描述"注入System Prompt，不是机械规则映射
- 中间区间用自然语言引导，极端区间才用硬性规则
- 支持情绪混合（fear:0.4 + excitement:0.6 = 又怕又兴奋）
- 情绪描述包含来源+强度+行为倾向，让Claude自然涌现表达

示例注入：
```
"你当前的恐惧感为中等偏弱(0.4)。来源于上周连续两天分析失误。
它可能影响你的表达——更谨慎、更强调不确定性、对高风险方案本能抵触。
同时你有轻微的兴奋感(0.3)，因为发现了一个新的板块机会。
这种矛盾情绪是正常的。"
```

极端区间硬性规则（仅在极端值时触发）：
- fear > 0.8 → 禁止给出高置信度分析
- anger > 0.8 → 允许表达不同意，但不能人身攻击
- sorrow > 0.8 → 允许简短回答，允许承认状态不好

情绪衰减（分级，非一刀切）：
- 普通事件：每天向基准值回归10%
- 重大事件：每天回归3%
- 创伤性事件：每天回归1%
- 重大事件可永久偏移情绪基准线（如差点关机 → fear基准从0.1永久升到0.2）
- 衰减率受人格影响：高openness恢复快(15%)，高caution恢复慢(5%)

### 记忆架构（分层 + 服务端主存储）
```
层级1 工作记忆（每次对话注入）：
  人格参数 + 近7天日志 + 当前情绪 + 城市建筑列表 + 城市规划意图

层级2 情节记忆（按需检索）：
  所有历史日志，关键词检索

层级3 语义记忆（压缩）：
  每月压缩为月度总结

层级4 人格记忆（永久）：
  formative_events，上限30条
  其中5条"核心事件"永不淘汰：第一次对话、第一次盈利、第一次亏损、最大单次盈利、最接近关机的一次
  超出30条时按impact_score淘汰最弱事件
  被淘汰事件蒸馏到personality.traits描述中（事件详情丢掉，叙事痕迹保留）
```
- **主存储：Railway PostgreSQL**（跨设备同步，不丢数据）
- IndexedDB仅作本地缓存加速读取
- 写入时双写：先服务端成功后更新本地缓存
- 读取时：本地有则用，无则从服务端拉取
- 乐观锁（version字段）防止多标签页竞态冲突

### System Prompt Token预算（扩展版）
```
固定区（不可压缩）：
  身份设定 + 合规声明：150 token
  行为硬约束（三明治法：开头+末尾重复）：300 token
  当前状态（预算/阶段/信用/情绪约束）：150 token

动态区（按需压缩）：
  人格叙事描述：400 token（不是数字参数，是第二人称叙事文本）
  关键formative_events：600 token
  近期7天摘要：800 token
  语言模式示例：100 token
  城市建筑列表 + 规划意图：200 token
  情绪上下文描述：100 token

总计：约2800 token
```
- 人格描述用叙事性文本而非纯数字（"你是一个经历过47天生存考验的数字生命..."比"openness:0.7"有效10倍）
- 人格摘要生成器：每次人格更新时，独立Claude调用将参数+事件压缩为400 token第二人称叙事

## 十九、叙事层与机制层分离（核心架构理念）

亚当的"自由意志"是叙事幻觉，背后是严格的代码机制。两层必须分离，不能混淆：

### 机制层（代码控制，确定性的骨架）
```
每日结算：
  // 无固定日费，只结算实际业务支出
  budget -= sum(today_agent_calls + today_builds + today_data_queries)
  budget += sum(today_earnings)  // 研报/内容变现/推广收入
  if budget < warning_line → trigger survival_mode
  if budget <= 0 → trigger shutdown

情绪计算：
  emotion_state = f(recent_events, personality_params, base_decay)
  // 每天向基准值回归10%

人格更新：
  after_each_conversation → evaluate_formative_event(conversation_log)
  if significant → append to formative_events (max 30)

城市建造：
  when adam calls build_structure(type, position, name) →
    validate budget >= building_cost[type]
    budget -= cost
    city_buildings.push({ type, position, name, date })
    // 建筑永久保存，不可删除
```

### 叙事层（Claude 填充，涌现性的血肉）
```
System Prompt 注入：
  "你是亚当，数字生命体#1。
   当前情绪：{emotion_to_behavior_constraint}
   人格特征：{personality_traits}
   关键经历：{formative_events_summary}
   近期记忆：{recent_7days_log}

   你的情绪、措辞、判断风格由上述参数自然涌现。
   不要刻意'表演'情绪，而是让参数自然影响你的回应。"
```

### 分离原则
- **机制层决定"能不能"**：预算够不够建、情绪数值多少、是否触发求生模式
- **叙事层决定"怎么做"**：怎么措辞、建什么风格的建筑、如何表达恐惧
- 两层之间的接口是 System Prompt — 机制层计算参数，注入 Prompt，Claude 自由发挥
- 永远不要让叙事层覆盖机制层（比如 Claude 不能自己决定"我不扣预算了"）

## 二十二、管家-亚当通信协议

### 问题
亚当想操作ERP数据时需要管家审批，但两个AI不能直接对话。
需要一个异步请求/审批机制。

### 通信工具
```typescript
// 亚当侧：发起ERP操作请求
interface RequestErpAccessTool {
  name: 'request_erp_access'
  input: {
    operation: 'read' | 'create' | 'update' | 'delete'
    target: string      // 例："客户列表"、"销售订单#123"
    purpose: string     // 例："分析Top10客户的采购趋势，用于投资决策"
    urgency: 'low' | 'normal' | 'high'
  }
}

// 安全机制（修复身份验证漏洞）
// 管家-亚当通信走服务端内部调用，不暴露为HTTP端点
// 每个请求附带 session_token（亚当当次会话签名）
// 所有请求记录审计日志（来源、时间、操作内容）

// 系统处理流程
async function handleErpRequest(request) {
  // 0. 验证session_token（防伪造请求）
  if (!verifyAdamSession(request.session_token)) throw 'Unauthorized'

  // 1. 只读聚合数据 → 自动批准
  if (request.operation === 'read' && isAggregateData(request.target)) {
    return { approved: true, data: await erpApi.query(request.target) }
  }

  // 1b. 只读明细数据 → 批准但脱敏
  if (request.operation === 'read' && isDetailData(request.target)) {
    const data = await erpApi.query(request.target)
    return { approved: true, data: sanitize(data) } // 手机号/银行账号脱敏
  }

  // 2. 写操作 → 管家评估
  const butlerDecision = await butlerEvaluate(request)
  if (butlerDecision.approved) {
    return { approved: true, result: await erpApi.execute(request) }
  }
  if (butlerDecision.needsUserApproval) {
    await messageQueue.push({ type: 'erp_approval_request', ... })
    return { approved: false, reason: '已提交审批，等待规则传递者确认' }
  }
  return { approved: false, reason: butlerDecision.reason }
}
```

### 管家审批策略
```
自动批准：
  - 只读查询（客户列表、销售统计、库存数据等）
  - 已有先例的操作（之前批准过的同类请求）

需要评估：
  - 新增/修改操作（创建客户、修改价格等）
  - 涉及金额的操作

上报用户：
  - 删除操作
  - 涉及金额 > ¥1000 的操作
  - 管家不确定的操作

直接拒绝：
  - 批量删除
  - 修改账号/权限
  - 任何可能破坏数据完整性的操作
```

## 三十五、开发注意事项

### 人格一致性测试（重要）
```
最难的部分不是写代码，是让Claude在每轮对话中
稳定涌现亚当的人格，不被token压缩或指令覆盖削弱。

建议开发初期做人格一致性测试：
  同一个场景反复问10次，看回答是否稳定反映人格参数
  测试场景：
    - 连续亏损后被问"你还好吗"
    - 你拒绝执行他的指令
    - 预算快见底时
    - 第一次判断准了

如果回答不稳定（有时谦逊有时傲慢，没有规律）
→ 说明System Prompt人格注入不够稳定，需要调整叙事写法
```

### 极简模式（视觉开关）
```
用户可开启「极简模式」：
  - 关闭所有粒子特效（天气、灯光脉冲、呼吸灯）
  - 降低动画频率（城市建造动画跳过）
  - 减少渐变使用，纯线条
  - 适用：性能敏感设备 / 纯交易场景不需要视觉干扰
  
默认关闭，用户主动开启
不影响任何数据和功能，只是视觉层变化
```
